# **Notes**

### **IRCA Triggering**

### **Authentication & Authorization**

* Confirm the management of **API keys, tokens, and session cookies** between IRCA components (e.g., Transparency, Perspective, agents).
* Ensure **multi-tenant security** is respected: each tenant’s data must be isolated.
* Validate **role-based permissions** — who can trigger, view, or perform remediation actions.
  + For example: some users should be able to *view reports* but *not execute remediation*.
* Which roles in Perspective can execute remediation?
* Is there a need to define a *dedicated IRCA role* for secure automation?
* How are tokens refreshed, revoked, and audited?

### **Data Collection:**

* When IRCA is triggered, how do we know what Transparency to call?
  If critical malop is triggered on end-point – it is challenging.
  If we collect critical malops / server detections from the server, the server has the endpoint ID, and we have to apply a logic to locate the relevant Transparency.
* How do we Map between malop names and their description? Does the “description” database exist?
  For the POC, we created two directories to manage MalOp and detection event descriptions:

1. **EDR MalOps** – Based on *CMS* and *Legacy* content. The Security Research team provided CSV files containing rule explanations, which were converted into JSON format. These JSON files are stored under: /IRCA/data/malop\_explaination\_json/
2. **Detection Events** – Covering detection engines such as *Fileless*, *Variant*, and *Pcpcore\_YML*. Unlike the EDR MalOps, **these descriptions were generated by an LLM** based on each rule’s logic and stored under: /IRCA/data/explanations/

* We should create an optimized API for the collection, preferably a single request.

### **Data Storage & Retention**

* Reports (PDF + JSON) are currently stored in a bucket; the team discussed saving both the **raw JSON** and the **rendered PDF**.
* Need to confirm **metadata tracking** — how do we know which report belongs to which tenant and user?
* Evaluate long-term storage in a **database** (e.g., MongoDB or Postgres) vs. temporary bucket storage.
* Where will IRCA reports be permanently stored?
* How will lifecycle management (TTL, cleanup, versioning) be handled?
* Can we ensure that links in the IR reports remain valid (stable IDs instead of transient URLs)?

### **Architecture Integration**

* Must confirm how IRCA integrates with Transparency and Perspective APIs.
* For multi-tenant deployment, determine whether triggers are handled *via the server* or *from the client*.
* Consider **micro-frontend** architecture to embed IRCA views inside Perspective without modifying its core code.

**Questions to Answer:**

* Can Perspective call IRCA’s microservice via internal service discovery?
* Will IRCA rely on Transparency’s service registry or require a new service layer?

### **AI/LLM Management**

* The LLM is currently called via Azure/OpenAI with prompts composed from detection data.
* Need to address **quota management**, **token budgeting**, and **license restrictions**.
* Decide on the hosting strategy for production (Azure vs. self-hosted model / Claude / OpenAI).

**Questions to Answer:**

* What are the projected monthly token costs for production use?
* How will error handling and fallback models be managed in production?

### **Remediation Automation**

* Currently user-triggered (manual confirmation per step).
* For production, determine if **auto-remediation** should ever occur and how to audit it.
* Each remediation action must validate the user’s privileges and execution results.

**Questions to Answer:**

* Should remediation always require manual confirmation?
* How do we log and audit remediation attempts?
* How do we handle partial permissions (e.g., user can run 3 of 7 steps)?
* Are we supporting all of the remediation API options?

### **Resilience & Error Handling**

* Must handle potential failures in API calls, invalid data, or timeout errors gracefully.
* Ensure retries, fallback mechanisms, and clear UI feedback.
* What happens if the Transparency API changes schema?
* How do we version and update API contracts between teams?

### **Deployment & Infrastructure**

* Code needs to be packaged into a **Docker image** with Kubernetes deployment.
* Secure access keys and environment variables.
* Determine CI/CD ownership: who maintains build, deploy, and rollback?

**Action Items:**

* Finalize Docker and Helm charts.
* Set up staging environment.
  Conduct load, latency, and cost testing.
